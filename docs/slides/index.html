🗺️ El problema

Un prompt suelto no alcanza para tres días

Improvisar con la IA sale caro: el contexto se pierde, el código crece sin que el equipo lo entienda y la demo se rompe justo antes del pitch.

Contar una experiencia propia: pedirle algo a la IA sin contexto y terminar reescribiendo todo. Idea central de la charla: darle al agente un plan y memoria.

🧭 Kiro

Dos formas de trabajar

Primero juega, después construye.

💬Para explorar

Modo Vibe

Conversas y el agente escribe el código. Ideal para probar una idea o hacer un cambio pequeño.

📐Para construir

Modo Spec

Primero requisitos, diseño y tareas. Después el agente implementa tarea por tarea.

Para SpookyThon: explora en Vibe y construye en Spec.

Mostrar la diferencia entre conversar (Vibe) y trabajar con una especificación (Spec). El spec es lo que evita perder el rumbo en tres días.
📄 Antes del spec

Primero el PRD y el TRD

Si sé el qué y el cómo, no me pierdo.

🎯Documento de producto

PRD

El qué y el para quién: problema, usuarios, funciones y qué queda fuera.

🛠️Documento técnico

TRD

El cómo: stack, arquitectura, datos, integraciones y límites técnicos.

📐Plan de trabajo

Spec

Con los dos listos, el agente arma requisitos, diseño y tareas.

Una página de cada uno alcanza para un hackathon. Son el contexto que el agente necesita para no inventar.

PRD es Product Requirements Document y TRD es Technical Requirements Document. Mostrar como ejemplo los de Termino, el proyecto de la demo: docs/termino-prd.md y docs/termino-trd.md. Se pueden escribir con ayuda del agente y luego usarlos como entrada del spec o como steering.
📐 Kiro · Specs

Un spec son tres archivos

Tú apruebas cada paso.

❓El qué

requirements.md

Historias de usuario y criterios de aceptación en notación EARS.

🏗️El cómo

design.md

Arquitectura, componentes, datos y decisiones técnicas.

✅El orden

tasks.md

Tareas pequeñas que el agente ejecuta una por una.

Revisas y corriges cada archivo antes de pasar al siguiente.

Los tres archivos viven en .kiro/specs dentro del repositorio, así que todo el equipo los ve y los versiona. El humano aprueba cada etapa.
🧰 Kiro

La caja de herramientas

¡Con esto ya no trabajo a ciegas!

📌

Steering

Archivos con tu producto, stack y estructura. El agente los lee siempre.

🪝

Hooks

Automatizaciones que se disparan con eventos, como guardar un archivo.

🔌

MCP

Conecta documentación, bases de datos y APIs externas.

✨

Powers

Paquetes que suman conocimiento especializado cuando la tarea lo pide.

🎓

Agent Skills

Instrucciones reutilizables que el agente carga según la tarea.

🚀

Autopilot

El agente avanza solo, sin pedir aprobación en cada paso.

Steering vive en .kiro/steering (product.md, tech.md, structure.md). Hooks: por ejemplo, generar tests al guardar. Powers agrupan herramientas MCP, steering y hooks. Autopilot es cómodo, pero conviene revisar los cambios al final de cada tarea.

🧙 Gentle-AI

¿Qué instala Gentle-AI?

Todo esto con un solo comando.

🌱

ODD

El flujo de todos los días: explorar, anotar tareas e implementar una por una.

📜

SDD

Desarrollo guiado por especificaciones, fase por fase.

🧪

TDD

Primero el test que falla, después el código que lo pasa.

🧾

RDD

Cuatro lentes revisan cada cambio antes de entregarlo.

🧠

Engram

Memoria que sobrevive entre sesiones.

🎓

Skills y subagentes

Guías reutilizables y un orquestador que reparte el trabajo.

Ejecutas gentle-ai, eliges tu agente (Kiro incluido) y queda todo listo.

Gentle-AI es un configurador de Gentleman Programming. No reemplaza a Kiro: lo configura. El mismo flujo funciona en otros agentes, así el equipo no depende de una sola herramienta. Las siguientes diapositivas abren cada pieza.
📜 Gentle-AI · SDD y TDD

SDD: una fase, un entregable

Fase 1

🔎 Explore

Investiga el código y compara caminos.

Fase 2

💡 Propose

Intención, alcance y enfoque.

Fase 3

📋 Spec

Requisitos y escenarios.

Fase 4

🏗️ Design

Decisiones de arquitectura.

Fase 5

🧩 Tasks

Lista ordenada de tareas.

Fase 6

⚒️ Apply

Escribe el código siguiendo el spec.

Fase 7

✅ Verify

Compara lo hecho con el spec.

Fase 8

📦 Archive

Cierra el cambio y guarda el estado.

TDD acompaña cada tarea: 🔴 test que falla → 🟢 código que lo pasa → ✨ limpieza.

SDD es el camino formal para cambios grandes; cada fase la ejecuta un subagente distinto. Relacionarlo con Kiro: requirements, design y tasks equivalen a las fases spec, design y tasks. TDD: cuando existe un test ejecutable y un resultado esperado claro, primero se ve fallar el test, después se implementa y al final se refactoriza.
🌱 Gentle-AI · ODD

ODD: Organic Driven Development

1

Autorizar

¿Me pidieron un cambio o solo investigar?

2

Explorar

Leer el código antes de proponer.

3

Aclarar

Una pregunta a la vez, si hay una duda real.

4

Clasificar

¿Trabajo pequeño o grande?

5

Anotar

Tareas en odd/tasks antes de escribir.

6

Construir

Tarea por tarea, con test primero y un commit.

7

Cerrar

Contar qué se verificó y qué falta.

Lo pequeño se queda pequeño. Lo grande deja una lista de tareas para retomar el trabajo si la sesión se corta. 💾

ODD es el flujo que Gentle-AI aplica a cada pedido, sin que lo pidas. El documento de tareas se guarda en odd/tasks y se copia a Engram. Cada tarea cierra con un commit convencional en una rama de feature. El push y el PR siguen siendo decisión humana.
⚖️ Comparación

Spec, SDD y ODD: ¿cuál uso?

📐 Spec de Kiro📜 SDD de Gentle-AI🌱 ODD de Gentle-AI
Qué esUn modo del IDE de KiroUn flujo formal de 8 fasesEl flujo por defecto, liviano
Qué dejarequirements, design y tasksPropuesta, spec, diseño, tareas y verificaciónUna lista de tareas en odd/tasks
Quién trabajaEl agente de Kiro; tú apruebas cada archivoUn subagente por faseEl orquestador; delega solo lo grande
Cuándo usarloFeatures dentro de KiroCambios grandes que piden trazabilidadEl día a día: arreglos y cambios medianos

No compiten: ODD para el día a día, SDD para lo grande y el Spec cuando trabajas dentro de Kiro.

Remarcar que los tres comparten la misma idea: planear antes de escribir código. El Spec de Kiro vive en .kiro/specs; SDD agrega exploración y propuesta antes, y verificación y archivo después; ODD es lo que Gentle-AI hace siempre, sin que lo pidas, y solo crea un documento de tareas cuando el trabajo es grande.
🧠 Gentle-AI · Memoria

El contexto que no se pierde

¡Me acuerdo de lo que hicimos ayer!

🧠Memoria

Engram

Guarda decisiones, bugs y hallazgos. La siguiente sesión empieza sabiendo qué pasó en la anterior.

🎓Conocimiento

Skills

Guías reutilizables en un registro. El agente carga solo las que la tarea necesita.

🕸️Mapa del código

CodeGraph

Un grafo del repositorio: símbolos, llamadas y qué se rompe si cambias algo.

En un equipo de tres, nadie tiene que explicarle lo mismo al agente en cada sesión.

Engram sobrevive entre sesiones y también cuando el contexto se compacta. Las skills son archivos SKILL.md; el registro vive en .atl/skill-registry.md. CodeGraph responde preguntas de estructura sin leer archivo por archivo.
🧾 Gentle-AI · RDD

Cuatro lentes antes de entregar

Cuatro miradas ven más que una.

🛡️

Riesgo

Seguridad, permisos y datos expuestos.

📖

Legibilidad

Nombres claros y código simple.

🧪

Fiabilidad

Tests, casos límite y regresiones.

🌧️

Resiliencia

Qué pasa cuando algo falla.

La revisión pide tu permiso en cada cambio y admite una sola corrección. Tú decides cuándo se entrega.

¿Una decisión difícil? Judgment Day: dos jueces revisan a ciegas y solo se aplica lo que ambos confirman. ⚖️

RDD es receipt-driven development: el usuario lo activa o desactiva con gentle-ai review mode. Aclarar con honestidad que la revisión nativa hoy corre en Claude Code, Codex, OpenCode y Pi; en Kiro se aprovecha el resto del ecosistema. La revisión es informativa: commit, push y PR siguen siendo decisión humana.
